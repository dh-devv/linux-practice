# 배포, Spring Boot, Git과 GitHub 기초

## 1. 전체 흐름 살펴보기

웹 서비스를 개발하고 사용자에게 제공하는 과정은 다음과 같이 생각할 수 있습니다.

```text
코드 작성 → Git으로 변경 이력 관리 → GitHub에서 코드 공유·협업
         → 애플리케이션 빌드·실행 → 서버에 배포 → 사용자가 서비스 이용
```

GitHub 사용과 배포는 서로 다른 작업입니다. 코드를 GitHub에 올렸다고 해서 애플리케이션이 자동으로 실행되거나 사용자가 이용할 수 있게 되는 것은 아닙니다. 별도의 배포 과정을 구성해야 합니다.

## 2. 배포(Deployment)

**배포**는 개발한 애플리케이션을 사용자가 이용할 수 있는 환경에 설치하고 실행하거나, 그 환경에 새 버전을 반영하는 과정입니다.

- **웹 서비스**: 서버 또는 클라우드 환경에 애플리케이션을 설치하고 실행해 사용자가 네트워크로 접근하도록 합니다.
- **모바일 앱**: 앱을 빌드해 앱스토어에 등록하고, 심사와 출시 과정을 거쳐 사용자가 설치할 수 있게 합니다.
- 배포 대상이 반드시 인터넷 전체일 필요는 없습니다. 회사 내부망이나 테스트 환경에 배포할 수도 있습니다.

### 웹 서비스 배포 예시

1. **개발**: 애플리케이션 코드를 작성하고 동작을 확인합니다.
2. **빌드**: 코드를 실행 가능한 형태로 만듭니다. 예를 들어 Spring Boot 프로젝트는 설정에 따라 JAR 파일로 패키징할 수 있습니다.
3. **서버 준비**: 애플리케이션을 실행할 환경과 필요한 프로그램을 준비합니다.
4. **배포 및 실행**: 빌드 결과물과 필요한 설정을 서버에 전달하고 애플리케이션을 실행합니다.
5. **접근 및 동작 확인**: 네트워크 설정과 서비스 동작을 확인합니다. 공개 서비스라면 도메인과 HTTPS 등의 설정도 검토합니다.
6. **운영 및 업데이트**: 로그와 상태를 확인하고, 수정한 새 버전을 다시 배포합니다.

> **빌드와 배포의 차이:** 빌드는 코드를 실행 가능한 결과물로 만드는 과정이고, 배포는 그 결과물을 사용 환경에 반영하는 과정입니다.

## 3. Spring Boot

**Spring Boot**는 자바(Java) 기반의 Spring 프레임워크를 사용해 애플리케이션을 더 쉽게 만들고 실행하도록 돕는 도구입니다. 웹 서버나 API를 개발할 때 자주 사용합니다.

- **프레임워크**는 프로그램을 개발할 때 활용하는 기본 구조와 공통 기능을 제공하는 기반입니다.
- Spring Boot는 필요한 설정의 상당 부분을 자동으로 구성해 초기 설정 부담을 줄여 줍니다.
- 내장 웹 서버를 사용하도록 구성할 수 있어, 별도의 웹 애플리케이션 서버 설치 없이 실행 가능한 형태로 만들 수 있습니다.

### 호환성을 고려해야 하는 이유

프로젝트를 개발하고 배포할 때는 사용하는 구성 요소의 버전이 서로 맞아야 합니다. 예를 들어 Spring Boot 버전이 요구하는 Java 버전보다 낮은 Java를 사용하면 프로젝트를 실행할 수 없을 수 있습니다.

확인할 항목은 다음과 같습니다.

| 확인 항목 | 살펴볼 내용 |
| --- | --- |
| Java 버전 | 선택한 Spring Boot 버전이 요구하는 Java 버전을 충족하는지 |
| Spring Boot와 라이브러리 | 사용하는 라이브러리와 의존성이 해당 Spring Boot 버전과 호환되는지 |
| 빌드 도구 | Gradle 또는 Maven 버전이 프로젝트 구성과 호환되는지 |
| 서버 환경 | 배포 서버의 Java 버전과 환경 설정이 애플리케이션의 요구 사항을 충족하는지 |

버전별 요구 사항은 달라질 수 있으므로 실제 프로젝트에 적용할 때 해당 버전의 공식 문서를 확인합니다.

## 4. 형상 관리, Git, GitHub

### 형상 관리란?

**형상 관리**는 소프트웨어 개발 과정에서 코드와 설정 등 관리 대상의 변경 사항을 식별하고 추적·관리하는 활동입니다. 누가, 언제, 무엇을 변경했는지 확인하고 필요한 시점의 상태를 살펴보는 데 도움이 됩니다.

### Git과 GitHub의 차이

| 구분 | 설명 |
| --- | --- |
| **Git** | 파일의 변경 이력을 관리하는 분산 버전 관리 도구입니다. 로컬 컴퓨터에서도 사용할 수 있습니다. |
| **GitHub** | Git 저장소를 호스팅하고 코드 공유, 협업, 이슈 관리 등의 기능을 제공하는 서비스입니다. |

즉, **Git은 변경 이력을 관리하는 도구**이고, **GitHub는 Git 저장소를 공유하고 협업할 수 있는 서비스**입니다. GitHub 외에도 Git 저장소를 호스팅하는 다른 서비스를 사용할 수 있습니다.

## 5. 저장소(Repository)

**저장소**는 Git으로 관리하는 프로젝트와 그 변경 이력이 보관되는 공간입니다.

| 종류 | 위치 | 설명 |
| --- | --- | --- |
| **로컬 저장소** | 내 컴퓨터 | 파일을 수정하고 변경 내용을 커밋하는 곳 |
| **원격 저장소** | 원격 서버 | 다른 사람과 변경 이력을 공유하거나 백업하는 데 사용하는 저장소. GitHub 저장소가 한 예입니다. |

로컬 저장소와 원격 저장소는 별개입니다. 로컬에서 커밋해도 원격 저장소에는 자동으로 반영되지 않으며, 일반적으로 `push`를 해야 전달됩니다.

## 6. Git 핵심 용어

### 6.1 브랜치(Branch)

**브랜치**는 저장소에서 작업 흐름을 나누어 독립적으로 변경 사항을 관리할 수 있게 하는 기능입니다.

예를 들어 `main` 브랜치는 기준이 되는 코드로 두고, `feature/login` 브랜치에서 로그인 기능을 개발할 수 있습니다. 작업이 끝나면 변경 내용을 검토한 뒤 다른 브랜치에 합칠 수 있습니다.

```text
main           A ── B ───────── E
                    └── C ── D ┘
                      feature/login
```

위 그림에서 `feature/login`의 작업을 마친 후 `main`에 합칩니다. 실제 커밋 이력은 사용하는 병합 방식에 따라 다르게 나타날 수 있습니다.

### 6.2 머지(Merge)

**머지**는 한 브랜치의 변경 내용을 다른 브랜치에 통합하는 작업입니다. 예를 들어 기능 브랜치에서 완성한 내용을 `main`에 반영할 때 사용합니다.

같은 부분을 서로 다르게 수정하는 등 Git이 변경 내용을 자동으로 합칠 수 없는 경우 **충돌(conflict)**이 발생할 수 있습니다. 이때는 충돌한 파일을 확인하고 원하는 내용으로 수정한 뒤 병합을 완료해야 합니다.

### 6.3 클론(Clone)

**클론**은 기존 저장소를 내 컴퓨터에 복제해 로컬 저장소를 만드는 작업입니다. 보통 GitHub에 있는 원격 저장소를 처음 가져올 때 사용합니다.

```bash
git clone <저장소-URL>
```

저장소 URL을 실제 주소로 바꾸어 실행합니다. 클론하면 일반적으로 파일과 Git 이력을 가져오고 원격 저장소가 `origin`이라는 이름으로 등록됩니다.

### 6.4 커밋(Commit)

**커밋**은 작업한 내용 중 스테이징 영역에 올린 변경 사항을 로컬 저장소의 이력으로 기록하는 작업 또는 그 기록 자체입니다. Git은 각 커밋에서 추적 대상 파일의 상태를 기록하며, 커밋을 비교해 변경 내용을 확인할 수 있습니다.

```text
작업 디렉터리에서 수정 → 스테이징(git add) → 커밋(git commit)
```

- **작업 디렉터리**: 실제 파일을 작성하고 수정하는 공간입니다.
- **스테이징 영역**: 다음 커밋에 포함할 변경 사항을 준비하는 공간입니다.
- **커밋 이력**: 준비된 파일 상태를 기록한 결과입니다.

커밋된 시점의 내용을 나중에 확인하거나 복원할 수 있습니다. 다만 복원 방법에 따라 현재 작업 내용이나 이력이 달라질 수 있으므로 명령어를 실행하기 전에 영향을 확인해야 합니다.

```bash
git status                    # 변경 및 스테이징 상태 확인
git add <파일명>              # 해당 파일의 현재 변경 내용을 스테이징
git commit -m "변경 내용 설명" # 스테이징된 내용을 커밋
```

커밋 메시지는 `로그인 기능 추가`처럼 무엇을 변경했는지 알 수 있게 작성합니다. `git add` 이후 파일을 다시 수정했다면, 그 수정 내용도 커밋하려면 다시 스테이징해야 합니다.

### 6.5 푸시(Push)

**푸시**는 로컬 저장소의 커밋을 원격 저장소에 전달하는 작업입니다. 파일을 수정하거나 커밋만 한 상태에서는 원격 저장소에 자동으로 올라가지 않습니다.

```bash
git push origin main
```

위 명령은 로컬 `main` 브랜치의 커밋을 `origin` 원격 저장소의 `main` 브랜치로 전달합니다. 다른 브랜치를 사용한다면 그 브랜치 이름에 맞게 지정합니다.

> 비밀번호, API 키 등 비밀 정보는 커밋하거나 푸시하지 않습니다. `.gitignore`는 추적하지 않을 파일을 지정하는 데 도움이 되지만, 이미 추적 중인 파일은 목록에 추가하는 것만으로 추적이 중단되지 않습니다.

### 6.6 풀(Pull)

**풀**은 원격 저장소의 변경 사항을 가져와 현재 로컬 브랜치에 통합하는 작업입니다. 단순히 화면을 새로고침하는 것이 아니라, 가져온 이력을 현재 브랜치에 반영합니다.

```bash
git pull origin main
```

위 명령은 `origin`의 `main`을 가져와 **현재 체크아웃한 브랜치**에 통합합니다. 예를 들어 로컬 `main`을 갱신하려면 먼저 해당 브랜치로 전환해야 합니다. 로컬과 원격의 변경 내용이 충돌하면 직접 해결해야 할 수도 있습니다.

`git pull`은 원격 변경 사항을 가져오는 **fetch**와, 이를 현재 브랜치에 통합하는 과정으로 구성됩니다. 통합 방식은 설정이나 옵션에 따라 머지 또는 리베이스가 될 수 있습니다.

## 7. 자주 사용하는 작업 흐름

예를 들어 GitHub에 이미 만들어진 저장소에서 `main` 브랜치로 작업하는 경우입니다.

1. `git clone <저장소-URL>`로 저장소를 로컬에 복제하고, 생성된 디렉터리로 이동합니다.
2. `git switch main`으로 로컬 `main` 브랜치에 있는지 확인하고 전환합니다.
3. `git pull origin main`으로 원격 변경 사항을 가져와 통합합니다.
4. 파일을 수정하고 `git status`로 변경 사항을 확인합니다.
5. `git add <파일명>`으로 커밋할 변경 사항을 스테이징합니다.
6. `git commit -m "변경 내용 설명"`으로 로컬 이력을 만듭니다.
7. `git push origin main`으로 커밋을 원격 저장소에 전달합니다.

협업할 때는 프로젝트의 규칙에 따라 `main` 대신 별도 브랜치에서 작업하고, 변경 사항을 검토한 뒤 병합하기도 합니다. 원격에 다른 사람의 커밋이 먼저 올라왔다면 푸시가 거절될 수 있으므로 원격 변경 사항을 가져와 통합한 후 다시 시도합니다.

## 8. 핵심 요약

| 용어 | 핵심 의미 |

| 배포 | 애플리케이션을 사용 환경에 반영해 이용할 수 있게 하는 과정 |

| 형상 관리 | 소프트웨어 관리 대상의 변경을 추적하고 관리하는 활동 |
| Git | 파일의 변경 이력을 관리하는 분산 버전 관리 도구 |
| GitHub | Git 저장소 호스팅 및 협업 서비스 |
| 저장소 | 프로젝트와 Git 변경 이력을 관리하는 공간 |
| 브랜치 | 작업 흐름을 독립적으로 나누는 기능 |
| 머지 | 한 브랜치의 변경 내용을 다른 브랜치에 통합 |
| 클론 | 기존 저장소를 복제해 로컬 저장소 생성 |
| 커밋 | 스테이징된 파일 상태를 로컬 이력으로 기록 |
