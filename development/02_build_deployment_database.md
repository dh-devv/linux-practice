# 배포를 위한 빌드와 데이터베이스 기초

## 1. 빌드와 빌드 도구

### 빌드란?

**빌드(Build)**는 소스코드와 리소스를 실행하거나 배포할 수 있는 결과물로 만드는 과정입니다. 프로젝트에 따라 컴파일, 테스트, 의존성 처리, 패키징 등의 단계가 포함됩니다.

Java의 경우 소스코드를 일반적으로 JVM이 실행할 수 있는 **바이트코드**(`.class` 파일)로 컴파일한 뒤 JAR 또는 WAR로 패키징합니다. 따라서 빌드를 단순히 소스코드를 기계어로 변환하는 과정으로만 이해하면 안 됩니다.

```text
소스코드 작성 → 빌드(컴파일·테스트·패키징 등) → 빌드 산출물 → 서버에 배포·실행
```

**빌드 산출물**은 빌드 과정에서 생성되는 결과물입니다. Spring Boot 프로젝트의 JAR이나 WAR 파일이 대표적인 예입니다.

### 빌드 도구란?

**빌드 도구**는 컴파일, 테스트, 패키징과 같은 작업을 자동화하고 프로젝트에 필요한 라이브러리의 의존성을 관리하는 프로그램입니다. Java 프로젝트에서 많이 사용하는 도구로 Maven과 Gradle이 있습니다.

| 구분 | Maven | Gradle |
| --- | --- | --- |
| 설정 방식 | 주로 XML 형식의 `pom.xml` 사용 | Groovy DSL 또는 Kotlin DSL 사용 |
| 특징 | 정해진 구조와 규칙이 명확함 | 유연하게 빌드 작업을 구성할 수 있음 |
| 빌드 성능 | 프로젝트와 설정에 따라 다름 | 증분 빌드, 빌드 캐시 등의 기능을 활용할 수 있음 |

XML은 설정이 길어질 수 있고, Gradle의 DSL은 간결하게 표현하기 쉽습니다. 다만 가독성은 익숙한 방식과 설정의 복잡도에 따라 달라집니다. 빌드 속도 역시 프로젝트, 변경 사항, 캐시와 설정에 영향을 받으므로 Gradle이 항상 Maven보다 빠르다고 단정할 수는 없습니다.

## 2. Spring Boot 빌드 산출물: JAR과 WAR

| 구분 | JAR | WAR |
| --- | --- | --- |
| 의미 | Java Archive | Web Application Archive |
| 주된 용도 | Java 애플리케이션이나 라이브러리 패키징 | Java 웹 애플리케이션 패키징 |
| 실행 방식 | 실행 가능하게 구성된 경우 `java -jar`로 실행 | 일반적으로 외부 서블릿 컨테이너에 배포 |
| Spring Boot 활용 | 내장 서버를 포함한 실행 가능한 JAR을 자주 사용 | 외부 컨테이너 배포용으로 구성할 수 있음 |

### JAR

- JAR은 클래스 파일과 리소스 등을 묶는 형식입니다.
- **Spring Boot 실행 가능 JAR**은 애플리케이션 실행에 필요한 의존성을 포함하도록 패키징할 수 있으며, 웹 애플리케이션이라면 내장 웹 서버를 사용해 별도의 외부 서버 설치 없이 실행할 수 있습니다.
- 모든 JAR이 의존성을 포함하거나 독립 실행 가능한 것은 아닙니다. 실행 가능 여부는 패키징 방식과 진입점 설정에 따라 달라집니다.
- Spring Boot에서 JSP는 실행 가능한 JAR 패키징에 제약이 있습니다. JSP를 사용해야 한다면 Spring Boot 및 서블릿 컨테이너의 해당 버전 문서를 확인하고 WAR 배포 등을 검토합니다.

```bash
java -jar 애플리케이션.jar
```

위 명령은 서버에 적절한 Java 실행 환경이 설치되어 있고, 해당 JAR이 실행 가능하게 만들어졌을 때 사용합니다.

### WAR

- WAR은 웹 애플리케이션을 배포하기 위한 형식으로, 웹 리소스, 클래스, 라이브러리, 필요한 설정 등을 포함할 수 있습니다.
- 일반적으로 Tomcat과 같은 **서블릿 컨테이너**에 배포하여 실행합니다. 사용할 컨테이너와 애플리케이션의 버전 호환성을 확인해야 합니다.
- Spring Boot에서도 외부 컨테이너에 배포할 수 있도록 WAR을 구성할 수 있습니다. 설정에 따라 `java -jar`로도 실행 가능한 WAR을 만들 수 있으므로 WAR은 반드시 외부 컨테이너에서만 실행된다고 볼 수는 없습니다.
- JAR과 WAR 중 어느 쪽이 적합한지는 JSP 사용 여부, 기존 서버 환경, 배포 방식 등 프로젝트 요구사항에 따라 결정합니다.

**JSP(JavaServer Pages)**는 서버에서 동적인 웹 페이지를 생성하는 기술입니다. HTML과 함께 Java 코드를 사용할 수 있지만, 실제 프로젝트에서는 유지보수를 위해 코드를 분리하는 방식을 자주 사용합니다.

**서블릿(Servlet)**은 서블릿 컨테이너에서 실행되며 HTTP 요청을 처리하고 응답을 생성하는 Java 웹 기술입니다. 서블릿 컨테이너는 서블릿의 실행과 생명주기 등을 관리합니다.

## 3. HTTP 요청: GET과 POST

클라이언트는 서버에 HTTP 요청을 보내고, 서버의 웹 애플리케이션은 이를 처리해 응답을 반환합니다. Spring Boot의 서블릿 기반 웹 애플리케이션에서는 서블릿 컨테이너가 요청을 받아 애플리케이션에 전달합니다.

```text
클라이언트 → HTTP 요청 → 서버의 웹 서버·서블릿 컨테이너 → 애플리케이션 처리
클라이언트 ← HTTP 응답 ← 서버
```

| 메서드 | 일반적인 용도 | 데이터 전달 예시 |
| --- | --- | --- |
| **GET** | 리소스 조회 | URL의 쿼리 문자열: `GET /search?keyword=linux` |
| **POST** | 데이터 제출 또는 서버에서 처리 수행 | 요청 본문에 JSON 또는 폼 데이터 전달 |

- GET의 쿼리 문자열은 주소창에 표시될 수 있으며 브라우저 기록이나 서버 로그 등에 남을 수 있습니다. 따라서 비밀번호나 API 키처럼 민감한 정보를 URL에 넣지 않습니다.
- POST 요청 본문의 데이터는 주소창에 표시되지 않지만, 그것만으로 안전한 것은 아닙니다. 전송 중 보호하려면 **HTTPS**를 사용하고, 로그와 저장소에도 민감한 정보가 남지 않도록 주의합니다.
- GET과 POST는 데이터 위치뿐 아니라 요청의 의미도 다릅니다. GET은 조회에 사용하고, 데이터 생성·변경처럼 서버의 상태에 영향을 줄 수 있는 작업에는 보통 POST 등을 사용합니다.

## 4. 데이터베이스와 DBMS

**데이터베이스(DB)**는 관련 데이터를 체계적으로 저장하고 관리하는 데이터의 모음입니다. **DBMS(Database Management System)**는 데이터베이스를 생성·관리하고 데이터를 저장, 조회, 수정, 삭제할 수 있게 해 주는 소프트웨어입니다.

데이터 처리의 기본 작업은 **CRUD**라고 합니다.

| 작업 | 의미 | SQL 예시 |
| --- | --- | --- |
| Create | 데이터 생성 | `INSERT` |
| Read | 데이터 조회 | `SELECT` |
| Update | 데이터 수정 | `UPDATE` |
| Delete | 데이터 삭제 | `DELETE` |

### DBMS의 종류

- **RDBMS(관계형 데이터베이스 관리 시스템)**: 데이터를 테이블과 관계를 중심으로 관리합니다. MySQL, MariaDB, Oracle Database, Microsoft SQL Server 등이 있습니다.
- **NoSQL DBMS**: 문서, 키-값 등 관계형과 다른 데이터 모델을 사용하는 시스템을 통칭합니다.
- **시계열 데이터베이스**: 시간에 따라 기록되는 측정값이나 로그 등을 다루는 데 특화된 데이터베이스입니다. 분류에 따라 NoSQL과 겹칠 수 있습니다.

## 5. Ubuntu에 MariaDB 설치하기

다음 명령은 Ubuntu에서 `apt`와 `systemd`를 사용하는 환경을 기준으로 합니다. `sudo` 권한과 패키지 저장소에 접근할 수 있는 네트워크가 필요합니다.

```bash
# 패키지 목록 갱신
sudo apt update

# MariaDB 서버 설치 (-y: 설치 확인 질문에 자동 동의)
sudo apt -y install mariadb-server

# 서비스를 지금 시작하고 부팅 시 자동 시작하도록 등록
sudo systemctl enable --now mariadb
```

### 설치 및 실행 상태 확인

```bash
# 설치된 패키지 정보 확인
apt list --installed mariadb-server

# 현재 실행 상태와 최근 로그 확인
sudo systemctl status mariadb

# 현재 활성 상태 및 부팅 시 자동 시작 설정 확인
systemctl is-active mariadb
systemctl is-enabled mariadb

# 로컬 데이터베이스 접속 확인
sudo mariadb
```

`is-active`가 `active`, `is-enabled`가 `enabled`를 출력하면 각각 현재 실행 중이며 자동 시작이 설정된 상태입니다. `sudo mariadb`로 접속한 뒤 `SELECT VERSION();`으로 버전을 확인하고 `exit`으로 종료할 수 있습니다. 인증 방식은 설치 환경에 따라 다를 수 있습니다.

서비스가 실행되지 않으면 `sudo systemctl status mariadb`와 `sudo journalctl -u mariadb`로 상태와 로그를 확인합니다. 운영 환경에서는 계정과 권한, 인증 및 네트워크 접근 설정도 별도로 검토해야 합니다.

## 6. systemctl 명령어

`systemctl`은 Linux의 **systemd** 서비스 관리자를 제어하는 명령어입니다. 서비스의 현재 실행 상태와 부팅 시 자동 시작 여부는 서로 다른 설정입니다.

| 명령 | 설명 |
| --- | --- |
| `sudo systemctl start mariadb` | 서비스 시작 |
| `sudo systemctl stop mariadb` | 서비스 중지 |
| `sudo systemctl status mariadb` | 서비스 상태와 최근 로그 확인 |
| `sudo systemctl restart mariadb` | 서비스 재시작 |
| `sudo systemctl reload mariadb` | 서비스가 지원하는 경우 실행 중 설정 다시 읽기 |
| `sudo systemctl enable mariadb` | 부팅 시 자동 시작 등록 |
| `sudo systemctl disable mariadb` | 부팅 시 자동 시작 등록 해제 |

`enable`이나 `disable`만으로는 현재 실행 상태가 바뀌지 않습니다. 즉시 시작도 하려면 `enable --now`를 사용하고, 즉시 중지도 하려면 `disable --now`를 사용할 수 있습니다. `reload` 지원 여부와 실제 반영되는 설정은 서비스마다 다릅니다.

## 7. Windows에서 HeidiSQL 사용하기

**HeidiSQL**은 Windows에서 MariaDB 등의 데이터베이스에 접속해 데이터를 조회하고 관리할 수 있는 그래픽 클라이언트입니다. Windows에 HeidiSQL을 설치하고, Ubuntu의 MariaDB 서버에 접속할 세션을 구성할 수 있습니다.

접속하려면 서버 주소, 포트, 데이터베이스 계정과 인증 정보가 필요합니다. 서버의 원격 접속 설정, 계정 권한, 방화벽 및 Windows와 Ubuntu 사이의 네트워크 연결도 확인해야 합니다. 외부에 데이터베이스 포트를 무분별하게 공개하지 말고, 필요한 호스트에만 접근을 허용하거나 SSH 터널과 같은 안전한 접근 방식을 검토합니다.

## 8. Git에 올리지 않을 파일

- **빌드 산출물**: 프로젝트에서 직접 관리해야 하는 경우가 아니라면 빌드로 다시 만들 수 있는 결과물은 보통 제외합니다.
- **캐시와 임시 파일**: 환경에 따라 자동 생성되는 파일은 일반적으로 제외합니다.
- **민감한 정보**: API 키, 비밀번호, 개인 키, 실제 운영 환경의 인증 정보는 저장소에 올리지 않습니다.

`.gitignore`에 제외할 파일과 디렉터리를 기록할 수 있습니다. 다만 이미 Git이 추적 중인 파일은 `.gitignore`에 추가해도 자동으로 추적이 해제되지 않습니다. 민감한 정보가 커밋되었다면 파일을 삭제하거나 무시하는 것만으로는 과거 이력에서 사라지지 않으므로, 해당 인증 정보를 즉시 폐기·교체하고 이력 처리도 검토해야 합니다.

> **Git과 GitHub의 비용:** Git은 무료 오픈소스 버전 관리 도구입니다. GitHub는 Git 저장소 호스팅과 협업을 제공하는 서비스이며, 무료 요금제와 추가 기능을 위한 유료 요금제가 있습니다.

## 핵심 요약

1. 빌드는 코드를 실행·배포 가능한 결과물로 만드는 과정이며, Maven과 Gradle은 이를 자동화합니다.
2. Spring Boot의 실행 가능 JAR은 내장 서버를 사용할 수 있고, WAR은 외부 서블릿 컨테이너에 배포할 수 있습니다.
3. GET은 주로 조회, POST는 데이터 제출과 처리에 사용합니다. 민감한 데이터는 URL에 넣지 않고 HTTPS로 보호합니다.
4. MariaDB는 RDBMS이며, Ubuntu에서는 `apt`로 설치하고 `systemctl`로 실행과 자동 시작을 관리합니다.
5. 빌드 결과물과 캐시는 필요에 따라 제외하고, 비밀번호와 API 키는 Git에 올리지 않습니다.
